# 儲存研究：Workers KV 與 D1

- 查核日期：2026-09-26
- 範圍：subs-tracker 是否要加入 Cloudflare D1，以及每一種資料要放在 KV 還是 D1。一併評估產品負責人的前提：「使用者資料這類很少變動的資料放 D1」。
- 前提條件：只有一個使用者，由部署者自架；手機優先的 PWA；Cron 每小時執行一次（`wrangler.toml`）。
- 標記：
  - 〔查證〕：來自 Cloudflare 官方文件或本 repo 原始碼，附出處。
  - 〔實測〕：在 scratchpad 的專案複本中執行得到的結果。本 repo 的檔案沒有變更。
  - 〔推論〕：由查證事實推得，沒有直接證據。
- 驗證方法：閱讀 Cloudflare 文件（2026-09-26 從 `developers.cloudflare.com/<path>/index.md` 下載），閱讀 `src/` 原始碼。另在 scratchpad 複製專案（`git ls-files`，`node_modules` 以 symlink 連到本 repo），加入 D1 binding 與一個測試路由，執行 `wrangler d1 migrations apply --local`、`vite dev`、`vite build`、`vite preview`、`wrangler deploy --dry-run`、`bun test`。沒有部署到 Cloudflare，沒有使用遠端 D1。

## 1. 摘要與建議

### 1.1 最重要的發現

1. **Cron 會覆寫使用者剛做的修改。** Cron 在開始時讀取整個 `subscriptions` 陣列，送完所有通知後，才把它計算出的訂閱物件整筆寫回（`src/index.tsx:103-128`、`src/services/subscription.ts:41-76`）。在這段時間內，使用者對同一筆訂閱的修改會被 Cron 的舊版本蓋掉〔查證：原始碼〕。這正是產品的主要流程：「收到提醒後在手機上查看與修改訂閱」（`PRODUCT.md`）。時間窗是送出所有通知所需的時間，通常是幾秒〔推論〕。KV 沒有條件寫入，官方文件寫明「concurrent writes to the same key can end up overwriting one another… the last write will take precedence」〔查證：KV Write key-value pairs〕。
2. **產品負責人的前提與文件相反。** KV 文件寫明 KV 適合「write relatively infrequently, but read quickly and frequently」，並把「Storing application configuration」「Storing user preferences」列為適合的用途〔查證：How KV works〕。「很少變動」是選 KV 的理由，不是選 D1 的理由。本 app 的風險全部在**常被寫入、有兩個寫入者**的資料（訂閱與 Cron 狀態），不在帳號資料。只把帳號搬到 D1，要付出 D1 的全部成本，卻不能解決任何一個風險。
3. **D1 能直接解決的問題**：以欄位為單位的 `UPDATE`（Cron 只寫它自己的欄位）、`batch()` 是交易〔查證：D1 Database API〕、`DELETE … RETURNING` 可一次性取用 challenge〔實測，本機〕、Time Travel 提供 7 天（免費方案）的時間點還原〔查證：Time Travel、Limits〕。KV 沒有備份或還原功能〔推論：KV 文件沒有這類功能〕。
4. **目前的 `wrangler.toml` 環境設定是壞的，與 D1 無關。** `[env.production]` 與 `[env.staging]` 沒有 `kv_namespaces`。Binding 不會被環境繼承〔查證：Wrangler configuration「Non-inheritable keys」〕。實測 `CLOUDFLARE_ENV=production vite build` 的輸出是 `"kv_namespaces": []`、`"vars": {}`〔實測〕。另外，使用 Vite plugin 時，`wrangler deploy --env` 沒有效果〔查證：Vite plugin「Cloudflare Environments」〕，所以 `AGENTS.md` 中 `--env production` 的指令與實際建置不一致。加入 D1 時，這個問題會同樣發生在 D1 binding。
5. **測試可行。** `bun test` 內呼叫 `wrangler` 的 `getPlatformProxy()` 可以取得本機 D1，並執行 migration SQL〔實測：bun 1.4.2、wrangler 4.141.0〕。直接使用 `miniflare@5.20260925.0-alpha` 的 `new Miniflare({ d1Databases })` 在 Node 與 bun 都被參數驗證拒絕，原因未查明〔實測〕。

### 1.2 建議

**採用 D1，作為所有持久資料的唯一儲存。KV 只保留為舊資料的匯入來源，不再寫入。**

- 優先順序依風險決定，不依「變動頻率」決定：先搬訂閱與 Cron 狀態（第 1 點的風險），再搬設定與帳號、passkey。
- 設定與帳號也搬到 D1，理由是**只有一個儲存**：一套備份（Time Travel）、一個匯出來源、一套測試方法。另一個理由：密碼雜湊用 `JWT_SECRET` 當 HMAC 金鑰（`src/utils/crypto.ts:146-169`），兩者必須放在同一筆紀錄〔查證：原始碼〕。
- WebAuthn challenge 也放 D1，用 `DELETE … RETURNING` 做一次性取用。KV 的「讀取後刪除」不是原子操作（`src/services/webauthn.ts:199-214`）〔查證：原始碼〕。
- 查詢層用 D1 原生的 prepared statement，不用 ORM（第 5.4 節）。
- 與 `docs/design/screens.md` 第 6 節的資料模型變更（目前收在 `git stash`：「wip: 訂閱資料模型（等 D1 研究結果）」）一起做。第 6 節本來就要改變儲存格式，合併成一次遷移，比先改 KV 格式、再搬 D1 少一次遷移〔推論〕。
- 規模：9 個單位（第 6 節）。不採用 D1、只修補 KV 的方案是 4 個單位（第 7 節）。

這不是「不做就會壞」的決定。單一使用者之下，第 1.1 節第 1 點發生的機率低。選 D1 的主要收益是：Cron 與使用者不再互相覆寫、有時間點還原、新增的持久狀態（排程結果、提醒紀錄、passkey 欄位）有一致的放法。如果不想增加自架者的部署步驟，第 7 節的 KV 方案可以處理第 1 點，但沒有還原功能。

## 4. 產品負責人的前提（問題 3）

前提：「很少變動的資料（例如使用者資料）放 D1」。

### 4.1 文件怎麼說

- KV：「KV is suitable for use cases where you need to write relatively infrequently, but read quickly and frequently」；適合「Storing application configuration」「Storing user preferences」〔查證：How KV works〕。Storage options 的表格：KV 適合「Configuration data」〔查證〕。
- D1：適合「Persistent, relational storage for user data, account data, and other structured datasets」「Use-cases that require querying across your data ad-hoc」「Workloads with a high ratio of reads to writes」〔查證：Storage options〕。表格：「Relational data, including user profiles, product listings and orders」〔查證〕。
- KV 不適合的情況：「atomic operations」「read and written in a single transaction」，以及同一個 key 每秒寫入數十次的工作負載〔查證：How KV works〕。

### 4.2 評估

- 兩邊的文件都提到「使用者資料」可放 D1。但 D1 的理由是**關聯結構與 SQL 查詢**，不是「很少變動」。「很少寫入、經常讀取」是 KV 的設計目標。
- 本 app 只有一個帳號，沒有使用者表，也沒有關聯（`PRODUCT.md`「只有一個使用者」）。帳號資料沒有需要 D1 的特性。
- 真正需要 D1 特性（條件寫入、交易、多個寫入者）的是訂閱與 Cron 狀態，它們是**經常變動**的資料。
- 所以依照前提本身的做法（帳號放 D1、訂閱留在 KV）會增加一個 binding、一套 migration、一個部署步驟，但第 2.2 節的風險一個也不會減少。

### 4.3 建議

不採用「依變動頻率分配」的規則。改用：

1. 有兩個寫入者、需要條件寫入或交易的資料，放 D1。
2. 採用 D1 之後，其餘的持久資料也放 D1，理由是只維護一個儲存。
3. KV 不再寫入，只作為舊版本資料的匯入來源。

## 5. 採用 D1 的成本（問題 4）

### 5.1 Schema 草案

依 `docs/design/screens.md` 第 6 節與 stash 中的新型別（`PeriodUnit` 含 `week`、`reminder: 'default' | 'off' | number`、`paymentMethod` 自由文字、`cancelByDate`、`price: number`）設計〔推論〕。`STRICT` 表格在本機 D1 可以建立〔實測〕，遠端未驗證。

```sql
-- migrations/0001_init.sql
CREATE TABLE settings (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  admin_username TEXT NOT NULL,
  admin_password_hash TEXT NOT NULL,     -- HMAC-SHA256，金鑰是 jwt_secret
  jwt_secret TEXT NOT NULL,
  timezone TEXT NOT NULL DEFAULT 'UTC',
  reminder_hour INTEGER NOT NULL CHECK (reminder_hour BETWEEN 0 AND 23),
  reminder_mode TEXT NOT NULL DEFAULT 'ONCE' CHECK (reminder_mode IN ('ONCE', 'DAILY')),
  default_reminder_days INTEGER NOT NULL DEFAULT 3 CHECK (default_reminder_days BETWEEN 1 AND 365),
  webauthn_user_handle TEXT,             -- passkey 研究 7.4：固定的 user handle
  updated_at TEXT NOT NULL
) STRICT;

CREATE TABLE notification_channels (
  channel TEXT PRIMARY KEY CHECK (channel IN ('telegram', 'email', 'webhook', 'bark')),
  enabled INTEGER NOT NULL DEFAULT 0,
  config TEXT NOT NULL DEFAULT '{}',     -- JSON：憑證與進階欄位，由使用者寫入
  last_status TEXT CHECK (last_status IN ('ok', 'failed')),  -- 由 Cron 寫入
  last_error TEXT,
  last_attempt_at TEXT,
  updated_at TEXT NOT NULL
) STRICT;

CREATE TABLE subscriptions (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  category TEXT NOT NULL DEFAULT '',
  currency TEXT NOT NULL,
  price REAL NOT NULL,
  period_value INTEGER NOT NULL CHECK (period_value >= 1),
  period_unit TEXT NOT NULL CHECK (period_unit IN ('day', 'week', 'month', 'year')),
  start_date TEXT,
  expiry_date TEXT NOT NULL,             -- 下次扣款日，YYYY-MM-DD
  cancel_by_date TEXT,
  auto_renew INTEGER NOT NULL,
  is_free_trial INTEGER NOT NULL DEFAULT 0,
  is_active INTEGER NOT NULL DEFAULT 1,
  reminder_kind TEXT NOT NULL DEFAULT 'default' CHECK (reminder_kind IN ('default', 'off', 'days')),
  reminder_days INTEGER CHECK (reminder_days BETWEEN 1 AND 365),
  payment_method TEXT NOT NULL DEFAULT '',
  website TEXT NOT NULL DEFAULT '',
  notes TEXT NOT NULL DEFAULT '',
  last_reminder_sent_at TEXT,            -- 由 Cron 寫入
  last_checked_expiry_date TEXT,         -- 由 Cron 寫入
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
) STRICT;

CREATE TABLE reminder_deliveries (
  subscription_id TEXT NOT NULL REFERENCES subscriptions(id) ON DELETE CASCADE,
  local_date TEXT NOT NULL,              -- 使用者時區的日期
  channel TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('sent', 'failed')),
  error TEXT,
  attempted_at TEXT NOT NULL,
  PRIMARY KEY (subscription_id, local_date, channel)
) STRICT;

CREATE TABLE cron_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  local_date TEXT NOT NULL,
  started_at TEXT NOT NULL,
  finished_at TEXT,
  reminded INTEGER NOT NULL DEFAULT 0,
  failed INTEGER NOT NULL DEFAULT 0,
  error TEXT
) STRICT;

CREATE TABLE passkey_credentials (
  id TEXT PRIMARY KEY,                   -- credential ID，base64url
  public_key TEXT NOT NULL,
  counter INTEGER NOT NULL DEFAULT 0,
  transports TEXT NOT NULL DEFAULT '[]', -- JSON 陣列
  rp_id TEXT NOT NULL,
  aaguid TEXT,
  nickname TEXT,
  device_type TEXT,
  backed_up INTEGER,
  user_agent TEXT,
  created_at TEXT NOT NULL,
  last_used_at TEXT
) STRICT;

CREATE TABLE webauthn_challenges (
  challenge TEXT PRIMARY KEY,
  type TEXT NOT NULL CHECK (type IN ('registration', 'authentication')),
  expires_at INTEGER NOT NULL            -- Unix 秒
) STRICT;
```

設計說明：

- `settings` 只有一列（`CHECK (id = 1)`）。本 app 只有一個使用者，不建立使用者表。
- 使用者擁有的欄位與 Cron 擁有的欄位分開。Cron 只執行 `UPDATE subscriptions SET last_reminder_sent_at = ?, last_checked_expiry_date = ? WHERE id = ? AND expiry_date = ?`。使用者在這段時間改了下次扣款日，條件不成立，Cron 的更新不生效（`meta.changes` 為 0）〔實測：條件式 `UPDATE` 在本機回傳 `changes: 0`〕。
- 自動續訂推進 `expiry_date`，這是使用者擁有的欄位。Cron 寫入時加上 `AND updated_at = ?`（Cron 讀到的值），使用者修改過就放棄這次推進，下一次 Cron 再算〔推論〕。
- `price REAL` 沿用 stash 的 `number`。是否改用最小貨幣單位的整數，需要另外決定（`PRODUCT.md`「數字要正確」）。
- 資料只有幾十筆，除了主鍵以外不建立索引。全表掃描的 rows read 仍遠低於免費額度（第 5.8 節）〔推論〕。
- 本 schema 沒有 `meta` 表。「是否已匯入」由 `settings` 是否有列判斷（第 5.3 節）。

### 5.2 Migration 流程

〔查證：D1 Migrations、Wrangler D1 commands〕

- `wrangler d1 migrations create <DB> <name>` 在 `migrations/` 建立編號的 `.sql` 檔案。已套用的紀錄存在資料庫的 `d1_migrations` 表。
- `wrangler d1 migrations apply <DB> --local | --remote`。互動環境會先確認；CI 等非互動環境跳過確認。套用後會擷取備份。某個 migration 失敗時，該 migration 回復，之前成功的保留。
- 文件建議 migration 指令使用 binding 名稱，而不是資料庫名稱，這樣部署者改了資料庫名稱仍可執行〔查證：Deploy buttons「Running D1 Migrations」〕。
- `wrangler deploy` 不會自動套用 migration。Deploy button 文件的做法是把它放進 `deploy` script：`"deploy": "wrangler d1 migrations apply DB --remote && wrangler deploy"`〔查證：Deploy buttons〕。本 repo 的 `deploy` 是 `bun run build && wrangler deploy`，要改成先套用 migration。
- 規則：migration 只加不改。新增欄位用 `ALTER TABLE … ADD COLUMN`。需要改欄位型別時，建新表、複製、改名，並在同一個檔案完成〔推論〕。
- 部署順序：先套用 migration，再部署新 Worker。新 schema 必須與前一版的 Worker 相容，因為部署期間舊版本可能仍在執行〔推論〕。

### 5.3 KV 到 D1 的一次性資料遷移

目標：現有的自架部署升級後不必手動操作，且重複執行不會產生重複或覆蓋資料。

做法（在 Worker 內執行，不需要部署者執行指令稿）〔推論，關鍵行為有實測〕：

1. 每個需要設定的請求與 Cron 都先讀 `SELECT * FROM settings WHERE id = 1`。本來就要讀設定，所以不會多一次查詢。
2. 沒有這一列時，執行匯入：
   - 從 KV 讀取 `config`、`subscriptions`、`webauthn:user:<ADMIN_USERNAME>:credentials` 與其中每一筆 `webauthn:credential:<id>`。
   - 用現有的轉換函式把舊格式轉成新格式：`normalizeStoredSubscription()`（日期、`customType`）、`legacyReminderHour()`、`isReminderSet` + `reminderMe` → `reminder_kind` / `reminder_days`、`periodMethod` 代碼 → 文字、明文密碼 → 雜湊。
   - 舊憑證的 `rp_id` 依 passkey 研究第 7.4 節的規則補上（`WEBAUTHN_RP_ID`，空白時用 `psl.get(目前主機名稱)`）。
   - KV 是空的（全新安裝）時，只建立預設設定，並產生新的 `jwt_secret`。
3. 所有寫入放在**一個** `db.batch([...])`：先 `INSERT OR IGNORE` 所有訂閱、憑證、通知管道，最後 `INSERT OR IGNORE` `settings`。`batch()` 是交易，任何一個陳述式失敗，整批回復〔查證：D1 Database API；實測：本機重複主鍵使整批回復〕。所以不會出現「有設定、缺訂閱」的半完成狀態。
4. 匯入後**重新讀取** `settings`，不使用自己產生的值。兩個請求同時匯入時，D1 依序執行兩個 batch〔查證：「each individual D1 database is inherently single-threaded」〕，第二個 batch 全部被 `OR IGNORE` 略過，兩個請求讀回同一個 `jwt_secret`。這同時修正第 2.2 節的首次啟動問題。
5. KV 的舊資料不修改、不刪除。

限制與殘留風險：

- 每個陳述式最多 100 個綁定參數〔查證：D1 Limits〕。一筆訂閱約 22 個參數，每筆一個陳述式即可。
- 免費方案每個 invocation 最多 50 次 D1 查詢〔查證：D1 Limits〕。一個 `batch()` 算一次還是多次：未驗證。匯入只用一次 `batch()`。
- 回到舊版本：舊版本讀 KV，看不到匯入後在 D1 做的修改。回退只適合在升級後立即發現問題時使用〔推論〕。
- 部署過程中，舊版 Worker 可能在某些地點短暫繼續寫 KV。匯入後才寫入 KV 的修改會遺失。單一使用者在部署當下操作的機率低〔推論〕。
- 匯入在哪個地點執行，就讀那個地點的 KV 快取。舊版本不再寫入後，這不影響結果〔推論〕。

### 5.7 自架者的部署步驟

新安裝（CLI）：

1. `wrangler d1 create subs-tracker --binding DB --update-config`：建立資料庫，並把 binding 寫入設定檔〔查證：`d1 create` 的 `--binding`、`--update-config`〕。資料庫的主要執行個體建在接近執行指令的地點〔查證：Data location〕；台灣的使用者可以加 `--location apac`。
2. `bun run deploy`（先套用 migration，再部署）。

另一個選項：binding 不寫 `database_id`，由 `wrangler deploy` 自動建立資料庫並把 ID 寫回設定檔〔查證：Wrangler configuration「Automatic provisioning」〕。但 migration 必須在資料庫存在之後執行，而 `deploy` script 先執行 migration。這個順序在第一次部署是否可行：未驗證。建議文件使用步驟 1 的明確做法。

Deploy button：文件說會自動建立 D1，並執行 `package.json` 的 `deploy` script〔查證：Deploy buttons〕。從 dashboard 部署時，資源 ID 不會寫回 repository〔查證：Automatic provisioning〕。

既有安裝的升級：

1. 同新安裝的步驟 1、2。
2. 第一次開啟 app 或下一次 Cron 時，Worker 自動匯入 KV 資料（5.3）。
3. KV binding 保留。移除 KV binding 要等到之後的 major 版本，並在 changelog 說明「先升級到 X 版並開啟一次 app」〔推論〕。

環境設定（第 1.1 節第 4 點）必須一起處理：

- 做法 A：刪除 `[env.production]`、`[env.staging]`，只保留頂層。`bun run deploy` 本來就部署頂層（`AGENTS.md`）。
- 做法 B：每個環境各自寫 `[[env.<name>.kv_namespaces]]` 與 `[[env.<name>.d1_databases]]`，並用 `CLOUDFLARE_ENV=<name> vite build` 選擇環境。`wrangler deploy --env` 對 Vite 建置沒有效果〔查證〕。

### 5.8 免費額度與本 app 的用量

用量假設：30 筆訂閱、每天 50 個 API 請求、每小時一次 Cron、每天 10 次修改〔推論〕。

| 項目                     | D1 免費額度〔查證：D1 Pricing、Limits〕 | 估計用量〔推論〕                                                     |
| ------------------------ | --------------------------------------- | -------------------------------------------------------------------- |
| Rows read                | 5,000,000 / 天                          | 約 3,200（每個請求：設定 1 列 + 訂閱 30 列；Cron 24 × 1 列 + 30 列） |
| Rows written             | 100,000 / 天                            | 約 200（修改、Cron 的 30 筆更新、每筆最多 4 個管道的發送紀錄）       |
| 儲存                     | 每個資料庫 500 MB，帳號 5 GB            | 數十 KB。空的資料庫約 12 KB〔查證：D1 FAQ〕                          |
| 每個 invocation 的查詢數 | 50                                      | 每個請求 1–3 次；Cron 一次讀取加一個 `batch()`                       |
| Time Travel              | 7 天                                    | —                                                                    |

目前 KV 的用量約每天讀取 175 次、寫入 20 次，也遠低於 KV 的免費額度〔推論〕。兩種方案都不會因為額度而失敗。超過 D1 免費額度時查詢會失敗，直到 UTC 00:00 重設〔查證：D1 Pricing FAQ〕。

### 5.9 延遲

- 沒有開啟 read replication 時，所有查詢都送到一個地點的主要執行個體〔查證：Read replication〕。Read replication 要在 dashboard 或 REST API 明確開啟，而且必須使用 Sessions API 才會使用副本〔查證：Read replication、D1 Database API `withSession()`〕。
- 建議不開啟 read replication。單一使用者不需要讀取擴充，而不開啟時所有查詢都讀到最新資料，不需要處理 bookmark〔推論〕。
- 實際延遲：未量測（沒有部署）。

仍然存在的限制：

- 使用者在兩個裝置幾乎同時修改時，後寫入的覆蓋前者。KV 沒有條件寫入，在值裡放版本號再比對，仍是先讀後寫，只能縮小時間窗。
- Challenge 的取用不是原子操作。
- 「同一天不重複發送」只能靠 `reminder-state`；Cron 如果在發送後、寫入前失敗，下一次會重送〔推論〕。這點在 D1 方案也一樣：發送通知是外部副作用，無法與資料庫寫入放在同一個交易，只能做到至少一次。
